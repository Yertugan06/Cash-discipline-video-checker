# Прототип: проверка кассовой дисциплины по видео (локально, на GPU ноутбука)

Сервис принимает запись с камеры кассового узла и возвращает JSON по ТЗ: вердикт, список возможных нарушений с таймкодом,
описанием, пунктом нормы (со ссылкой на adilet.zan.kz) и кадрами-доказательствами. Всё работает на локальной машине:
модель Qwen3-VL 4B (Apache-2.0) через Ollama, без облачных API, без распознавания лиц и звука. Загруженное видео удаляется сразу после обработки.

Результат — подсказка для проверяющего, а не окончательный вывод.

## Как это работает

```
видео ──ffmpeg──► кадры 2 fps (родное разрешение, длинная сторона ≤ 1280)
      ──► выбор кадров: шаг 1,5 с; неизменившиеся кадры не отправляются в модель (состояние копируется)
      ──► 1) анкета состояния кадра, Qwen3-VL 4B, JSON-схема из 17 полей (~3 с на кадр):
             кассир за столом / в комнате, люди на стороне кассира, клиенты, человек в двери, инкассатор,
             деньги / сумка / документы / личные вещи / еда на столе, телефон, счётная машина, сейф, экран, дверь, деньги в руках
      ──► 2) проверки крупным планом (~1 с): модель один раз находит рамки стола, сейфа, ноутбука и двери,
             дальше кадр обрезается по рамке и задаётся узкий вопрос — только в нужные моменты:
             стол (деньги, сумка) — когда кассир выходит и когда подходит новый клиент;
             сейф — каждые 3 с; экран — пока кассира нет за столом; дверь — через 3–9 с после входа кассира;
             удостоверение личности — в каждой сессии с клиентом, до первого «да»
      ──► таймлайн состояний ──► правила (brev_kit/scripts/timeline_rules.py) ──► кандидаты нарушений с таймкодом
      ──► 3) подтверждение кандидата «посторонний»: сколько людей стоит и сидит на 4 кадрах (клиент садится, посторонний стоит)
      ──► пункт нормы из проверенного кодекса (brev_kit/codex/codex_verified.json) ──► JSON по ТЗ
```

Модель не «придумывает» нормы: она только описывает состояние кадра, а нарушение и пункт нормы выбирают
детерминированные правила по кодексу. Поэтому ответ воспроизводим и объясним.

Почему так: 4B по целому кадру хорошо видит людей и крупные предметы (кассир за столом — 14/14 на эталонных кадрах),
но пропускает мелкие (пачка денег на столе — 1/3, ключ в замке — 0/2) и не различает действия по одному кадру.
Узкий вопрос по увеличенному кропу дешевле анкеты в 3 раза и закрывает мелкие объекты; поля, которые 4B не различает
(действие кассира, ключ, детектор), из анкеты убраны — ответ короче на ~19 % токенов.

## Требования

* NVIDIA GPU от 6 ГБ (проверено: RTX 4050 Laptop 6 ГБ, 16 ГБ RAM), драйвер с CUDA;
* [Ollama](https://ollama.com) ≥ 0.13 (MIT);
* Python 3.10+; ffmpeg и ffprobe в `PATH`;
* папка `brev_kit` рядом с `prototype` (схема анкеты, промпты, правила, кодекс норм).

## Установка (один раз)

```bash
pip install -r requirements.txt -r requirements-detector.txt
```

Без `requirements-detector.txt` (torch, transformers) сервис тоже работает, но без детектора людей — как v2.

```bash
ollama pull qwen3-vl:4b-instruct
```

Важно: нужен тег **`-instruct`**. Теги `qwen3-vl:4b` / `qwen3-vl:2b` — «думающие» версии: тратят ~500 токенов на рассуждение и возвращают пустой ответ.

## Запуск

1. Сервер модели (отдельное окно PowerShell): `prototype/start_ollama.ps1` — 2 параллельных запроса, flash attention, KV-кэш q8_0.
2. Сервис (из папки `ForteBankCase`):

```bash
python -m uvicorn --app-dir prototype app:app --host 127.0.0.1 --port 8080
```

3. Веб-интерфейс: http://127.0.0.1:8080 — перетащить видео, дождаться результата (прогресс по этапам).

При первом запуске создаётся ключ API в `prototype/api_key.txt` (он же печатается в консоли). Свой ключ можно задать переменной `API_KEY`.

## API

| Метод | Путь | Описание |
|---|---|---|
| POST | `/api/v1/analyze` | multipart, поле `file` (.mov .mp4 .m4v .avi .mkv .webm), заголовок `X-API-Key` → `{"job_id", "status": "processing"}` |
| GET | `/api/v1/jobs/{job_id}` | заголовок `X-API-Key` → `processing`, или `done` + `verdict`, `violations`, или `failed` + `error` |
| GET | `/health` | модель и длина очереди |

Коды ошибок: 401 — нет или неверный ключ; 400 — нет файла или неподдерживаемый формат; 404 — нет такой задачи.

```bash
curl -H "X-API-Key: КЛЮЧ" -F "file=@X-26.mov" http://127.0.0.1:8080/api/v1/analyze
```

```bash
curl -H "X-API-Key: КЛЮЧ" http://127.0.0.1:8080/api/v1/jobs/JOB_ID
```

Пример ответа (`image_base64` сокращён):

```json
{
  "job_id": "3f2a9c1d7b44",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Наличные/ценности оставлены без присмотра: кассир покинул рабочее место",
      "timecode_sec": 10.5,
      "description": "… Основание: Правила НБРК № 231 (кассовые операции и инкассация), п. 20 ч. 2 (прямая норма). Это подсказка для проверки человеком, а не окончательный вывод.",
      "evidence_frames": [{"timestamp_sec": 9.5, "image_base64": "/9j/4AAQ…"}],
      "norm": {"id": "231-20-2", "document": "Правила НБРК № 231 …", "punkt": "п. 20 ч. 2", "quote": "…", "url": "https://adilet.zan.kz/…", "strength": "direct"}
    }
  ]
}
```

Поля `type`, `timecode_sec`, `description`, `evidence_frames[timestamp_sec, image_base64]` — по ТЗ; `norm` — дополнительное поле со ссылкой на пункт нормы.
Задачи обрабатываются по одной (очередь в памяти): GPU ноутбука не тянет два видео одновременно без потери скорости.

## Трасса обработки (как система пришла к ответу)

Каждая обработка пишет трассу: для задач сервиса — `prototype/traces/<job_id>/`, для пакетного прогона — `<out>/traces/<видео>/`.
В интерфейсе ссылка «Трасса обработки» появляется сразу после загрузки — страница обновляется сама, пока идёт обработка.

* шаги и время каждого (подготовка, анкета, проверки крупным планом, подтверждения, доказательства);
* `boxes.jpg` — где модель нашла стол, сейф, ноутбук и дверь (если рамка не там — все проверки этого объекта бесполезны);
* `timeline.png` — матрица состояний: строки — поля анкеты, столбцы — время; точка — значение исправлено кропом; красная линия — нарушение;
* кропы с ответом модели и отметкой, какие отсчёты они исправили; кадры подтверждения «посторонний» с числом стоящих/сидящих;
* кадры-доказательства с рамкой объекта и подписью.

В трассе есть кадры видео, поэтому она хранится только на этой машине; `TRACE=0` выключает запись.

## Настройки (переменные окружения)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `VLM_MODEL` | `qwen3-vl:4b-instruct` | `qwen3-vl:2b-instruct` — быстрее, но заметно хуже на мелких объектах |
| `VLM_BASE_URL` | `http://127.0.0.1:11434` | адрес Ollama; для vLLM — `http://127.0.0.1:8000/v1` и `VLM_STRUCTURED=json_schema` |
| `VLM_WORKERS` | 2 | параллельные запросы; должно совпадать с `OLLAMA_NUM_PARALLEL` |
| `STEP` | 1.5 | шаг между кадрами, с; для длинных видео растёт автоматически (не больше `MAX_CALLS` кадров) |
| `MAX_CALLS` | 70 | бюджет запросов к модели на видео — держит худший случай в лимите 300 с |
| `DIFF_THR`, `MAX_GAP` | 3.0, 6 | кадр «не изменился» → состояние берётся с предыдущего, но запрос не реже раза в 6 с |
| `MAX_SIDE` | 1024 | размер картинки для модели (1024 точнее 768 на 7 п.п.) |
| `ZOOM` | 1 | проверки крупным планом и подтверждения; 0 — только анкета (быстрее, но хуже) |

## Пакетная оценка на датасете

```bash
python prototype/batch_eval.py --videos open/open/videos --out prototype/work/runs/proto_4b
```

Обрабатывает все 40 уникальных видео по одному (как у жюри), сохраняет таймлайны (`states/*.jsonl`), нарушения и время,
затем считает метрики (`report_videos.md`): вердикт, попадание таймкода ±1/3/5 с, совпадение пункта нормы, время на видео.
Пороги правил можно подбирать без GPU — по сохранённым таймлайнам:

```bash
python brev_kit/scripts/timeline_rules.py --states prototype/work/runs/proto_4b/states --out prototype/work/runs/proto_4b/violations_tuned
```

## Результаты на датасете (40 уникальных видео, 22 метки, RTX 4050 Laptop 6 ГБ)

| | v1: анкета + стол крупным планом | v2: + проверки крупным планом, подтверждение «постороннего» через VLM | **v3 (по умолчанию): + детектор людей D-FINE, «нет документа» только после подтверждения** |
|---|---|---|---|
| Верный вердикт | 65 % (TP 15, FN 6, FP 8, TN 11) | 70 % (TP 14, FN 7, FP 5, TN 14) | **80 %** (TP 16, FN 5, FP 3, TN 16) |
| Ложные на чистых видео | 42 % | 26 % | **16 %** |
| Метка найдена в ±3 с / ±5 с | 10 / 10 из 22 | 12 / 13 из 22 | **12 / 14 из 22** |
| Пункт нормы совпал (для найденных меток) | 9 из 10 | 10 из 12 | 10 из 12 |
| Время на видео: среднее / худшее | 56 с / 150 с | 66 с / 174 с | 67 с / 172 с (X-39, 79 с видео); X-14 (142 с видео) — 140 с; лимит 300 с |

Что дал детектор людей (D-FINE-S, ~8 мс на кадр): «два клиента» (X-18) теперь находится; «посторонний» (X-30)
подтверждается без запросов к VLM; на 19 чистых видео правила по людям не сработали ни разу (у 4B было 5 ложных «посторонних»);
люди за стеклом отсекаются по линии пола — в трассе они серые с подписью «за стеклом».

«Нет документа» выдаётся только после подтверждения: при ручной проверке все 7 его срабатываний оказались ложными
(4B принимает купюры за карточку), а настоящие случаи (X-2, X-34) оно не находило. Метки ручной проверки —
`brev_kit/data/extra_review_marks.csv`, подтверждённые доп. события — `brev_kit/data/gt_extra.csv`.

Пропуски (5): ключ в замке (X-22) и закрытость двери (X-32) — слишком мелко даже на кропе; пересчёт без клиента (X-34),
пересчёт без детектора (X-44), деньги прошлого клиента (X-38). Проверено и не помогло: вопрос к 4B по окну из 4 кадров
(способ пересчёта не различает, на всех кандидатах отвечает «машиной»), движение пикселей в области кассира
(X-34 не отделяется от обычных уходов клиента). Ложные (3): X-14 (кассир у сейфа в углу комнаты — 4B считает, что вышла),
X-25 (документы на столе), X-35 (еда).

## Лицензии и ограничения

* Qwen3-VL 4B Instruct — Apache-2.0; D-FINE (ustc-community/dfine-small-coco) — Apache-2.0; Ollama — MIT;
  PyTorch — BSD-3; transformers — Apache-2.0; FastAPI, Uvicorn — MIT; Pillow — HPND; NumPy — BSD.
* Нет детекторов объектов YOLO/Ultralytics, нет облачных API, нет распознавания лиц, звук не используется.
* Сервис слушает только 127.0.0.1. Видео удаляется после обработки, результаты хранятся только в памяти процесса.
